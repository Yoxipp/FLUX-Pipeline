0. Avant de commencer

0.1 Comment lire ce manuel

Artiste : lis la partie A dans l'ordre jusqu'à A5, puis va directement au chapitre de ton outil ou de ton logiciel. A19 (règles de travail) et A20 (dépannage) sont à connaître. A21 donne l'emplacement de chaque fonction.

TD, développeur, curieux : la partie B explique comment tout marche à l'intérieur : processus, fichiers, formats, API, USD, décisions d'architecture.

0.2 Légende des états

PARTIE A
Utilisation

Tout ce qu'il faut pour travailler au quotidien avec FLUX : organiser le projet, publier, récupérer le travail des autres, assembler en USD, suivre la production et rendre.

A1. FLUX en une page

FLUX est une application de bureau Windows qui remplace toutes les manipulations de fichiers à la main entre les logiciels de l'équipe. Elle :

  • crée le projet et son arborescence (assets, séquences, shots, départements) à partir de règles de nommage : les tokens ;
  • publie ton travail en versions numérotées qui ne sont jamais écrasées (v001, v002...) avec un pointeur LAST toujours à jour ;
  • importe le travail des autres dans ton logiciel en un clic (Maya, Houdini, ZBrush, Nuke, Painter, Designer, Mari, Marvelous, Photoshop) ;
  • assemble en USD les assets, les décors et les shots, prêts pour le lighting et le rendu Karma ;
  • suit la production : tableau des assets et des shots, casting, plages d'images, calendrier d'équipe, fil d'activité, chat, mentions.
ModelingMaya / ZBrush

TexturingPainter / Mari / Designer

Tout passe par FLUX : chaque flèche est un publish d'un côté et un import de l'autre. Personne ne copie ni ne renomme de fichier à la main.

Trois idées à retenir

  1. Le nom fait tout. Le nom d'un fichier porte ses tokens (projet, type, nom, tâche, version). FLUX en déduit où il doit vivre.
  2. Tu travailles en local, tu publies pour les autres. Ta scène de travail est à toi ; ce que les autres utilisent, c'est ton publish.
  3. On charge des produits, pas des morceaux. En USD, on charge un asset, un décor ou un shot entier. Les couches internes sont gérées par FLUX.

A2. Installer, lancer, mettre à jour

Installer

  1. Lance FLUX-Setup-x.x.xxx.exe (fourni par l'équipe, dossier FLUX_UPDATE du serveur ou de OneDrive).
  2. Au premier lancement, l'écran Premier lancement demande le workspace (dossier racine FLUX : local, OneDrive ou serveur du studio) et ton nom d'utilisateur.
  3. FLUX crée dans le workspace : DOSSIER_PROJETS/ (les projets), USER/ (réglages par personne), CONFIG/ (réglages d'équipe), FLUX_UPDATE/ (installeurs).

Lancer

Double-clic sur FLUX. L'app démarre un petit serveur local (invisible) qui fait le travail. Si un antivirus le bloque au démarrage, FLUX réessaie tout seul et affiche un bandeau « reconnexion » tant que le serveur ne répond pas.

Mettre à jour

Dépose le nouvel installeur dans <workspace>/FLUX_UPDATE/. Au lancement suivant, chaque poste propose la mise à jour : Oui lance l'installeur et ferme FLUX, Plus tard continue.

Choisir tes logiciels

Paramètres : coche les DCC que tu utilises. Les autres disparaissent du lanceur et de la barre d'état.

A4. Le projet : tokens, noms, arborescence

Un projet FLUX est un dossier dans DOSSIER_PROJETS/ avec deux fichiers de référence :

  • tokens.json : la liste des valeurs autorisées (classes d'assets, noms, séquences, shots, types, tâches) et les règles de nom ;
  • project.json : identité du projet (project_id stable), fps, résolution, unités USD (1 mètre par unité, axe Y), config couleur OCIO, presets Painter.

A5. Le process voulu : du travail au rendu

Voici le parcours d'un plan dans FLUX, tel qu'il est pensé pour l'équipe.

1. Préparer (responsable prod / lead)

  1. Créer le projet (Folder Manager, onglet de création). project.json et tokens.json sont générés.
  2. Créer les assets (Catégorie + Name), les séquences et les shots. Chaque shot reçoit son socle : un dossier par département + usd/lighting + stage.
  3. Dans Production : plages d'images des shots (1001-1050 par défaut), casting (quels assets dans quel shot, combien d'instances), responsables, calendrier.

2. Fabriquer les assets

GEO
Modeling Maya / ZBrush → publish GEO (USD léger : géo + squelette + poids si skinné). Aussi abc, obj, fbx, mb, ma.
SHADING
Textures Painter / Mari / Designer → publish par map (conversion .tx auto). Lookdev Houdini → publish SHADING (matériaux + assign, variantes).
RIG
Maya → publish RIG (squelette USD + scène .mb pour l'anim).
GROOM / CFX
Houdini / Marvelous → publish, proxy de groom généré.
Component
Page USD : « Nouveau component » une fois par asset. Ensuite chaque publish le met à jour tout seul.

3. Fabriquer les plans

LAYOUT
Caméra (shelf Maya CAM) + placement → publish LAYOUT (preset caméra).
ANIM
Publisher mode Shot, Task ANIM, case Perso : une anim par perso et par instance (DINGO_01, DINGO_02...).
CFX / FX / CROWD
Houdini : caches publiés dans le shot, FLUX Crowd pour les foules.
Stage du shot
Régénéré automatiquement après chaque publish du shot : tout le plan en un fichier USD.

4. Lighting, rendu, compositing

  1. Production, séquence : Scène de rendu Houdini crée <SEQ>_render.hip (lumières communes, un bloc par shot, Karma, AOV, cryptomattes).
  2. Light rig de séquence + light rig de shot par-dessus. Publish LIGHT.
  3. Rendu Karma (local aujourd'hui ; farm Tractor prévu), sortie .exr.
  4. Nuke : Read du rendu publié, comp, Write publié en COMP.
Chaque étape consomme les LAST des étapes précédentes : un nouveau publish de modeling arrive automatiquement dans le lighting sans rien refaire. Pour le rendu final, FLUX figera les LAST en vNNN pour que rien ne bouge pendant le calcul.

A6. Accueil (Hub) et chat d'équipe

  • Publishs récents du projet actif : qui, quoi, quand. Clic = ouvrir l'emplacement.
  • Chat du projet : un chat par projet (teamChat.json du projet), vide sans projet actif. Tape @nom pour mentionner quelqu'un : il reçoit la mention dans Activité.
  • Bouton de rafraîchissement : les données se mettent à jour seules (interrogation régulière du serveur), le bouton force la relecture.

A7. Folder Manager

L'explorateur du projet, qui connaît les règles FLUX.

Vues

Boutons en haut à droite : 1 vue, 2 empilées, 2 côte à côte, 4 vues. Chaque vue a son historique, sa barre de chemin, sa recherche, sa sélection. La vue active (cadre de couleur) pilote le panneau droit. Glisser d'une vue à l'autre : déplace (Ctrl = copie), dans le même projet.

Barre latérale du Folder Manager

  • Listes sauvegardées et favoris, presets d'arborescence, tailles de vignettes.
  • Token Finder : cherche par tokens (CLASS, NAME, TYPE...) au lieu de naviguer.
  • Onglets de création : projet, asset, séquence, shot.

Panneau droit

  • Infos du fichier ou dossier sélectionné.
  • Note de publish : qui a publié, quand, avec quel commentaire ; historique du même publish (replié).
  • LOG JSON du dossier.

Clic droit

  • Open in <logiciel> : sur un USD, FLUX propose d'abord le produit complet (asset, décor, shot) puis « couche seule ». Dans Houdini LOP : Reference / Payload / Sublayer. Dans Maya : aplati (défaut) ou proxy USD.
  • Renommer, copier, déplacer, supprimer (avec annulation), ouvrir dans l'explorateur Windows.

Depuis Production, le bouton Ouvrir dans le Folder Manager ouvre directement le dossier d'une séquence ou d'un shot.

A8. Publisher

Le Publisher envoie ton travail dans le projet avec le bon nom, au bon endroit, en version immuable.

Étapes

  1. Source : un logiciel connecté (pastille verte) ou un fichier local. Si plusieurs Maya / Houdini tournent, FLUX te demande lequel (scène ouverte affichée).
  2. Mode : Asset ou Shot.
  3. Les champs : Catégorie / Name / Task / Instance / Variante pour un asset ; Sequence / Shot / Task / Perso ou Variante pour un shot. Ils construisent le nom (A4). Le bouton i de chaque champ explique ce qu'il attend.
  4. Format et options (voir tableau).
  5. Commentaire (devient la note de publish), puis Publier. Un toast confirme la version écrite.

Chaque preset montre la liste de ce qu'il va exporter avant le publish (« A exporter »).

Anim

  • Activer ANIMATION remplit Start / End avec la première et la dernière clé ; bouton Clés pour relire.
  • Mode Shot, champ Perso : le bloc INSTANCES liste DINGO_01, DINGO_02... Un publish par instance cochée : SEQ0010_SHOT0020_ANIM_DINGO, ..._DINGO_02.
  • Les joints sont vérifiés contre le rig publié de l'asset.

Textures (Painter / Mari)

Tableau par map : cocher les maps, format, profondeur (seules celles que le format supporte), taille. Painter lit les presets du projet (FLUX_BEAUTY_MAPS, FLUX_UTIL_MAPS). Mari : node FLUX Export dans le graphe (menu FLUX), suivi de l'export tuile par tuile.

A9. Versions : vNNN et LAST

Chaque publish crée deux choses dans le même dossier plat :

assets/chara/DINGO/model/null/
  CHAR_GEO_DINGO_null_v001.usd      version 1, jamais modifiée
  CHAR_GEO_DINGO_null_v002.usd      version 2, jamais modifiée
  CHAR_GEO_DINGO_null_LAST.usd      pointe toujours vers la dernière
Type de fichierCe qu'est le LAST
USDun petit layer qui référence la vNNN (métadonnées recopiées)
Fichier simple (.mb, .abc, image)une copie + un fichier .flux.json qui dit de quelle version il vient
Séquence d'images, cache > 2 Go, .vdbun fichier .link vers la version
  • Utilise LAST pour travailler : tu reçois les mises à jour.
  • Utilise vNNN pour figer (rendu final, rétro-compat).
  • Houdini recharge les LAST à l'ouverture de la scène. Maya : bouton MAJ du shelf FLUX pour ré-importer tes imports FLUX en place.

A10. Importer dans un logiciel

Depuis l'app

Folder Manager, clic droit sur un publish → Open in <logiciel>. Le logiciel doit être ouvert et connecté (pastille verte).

Houdini : HDA FLUX Import

ContexteFonctionnement
/stage (LOP)Type (Asset / Décor / Shot) → Classe ou Séquence → Élément → Version. Asset / décor = reference sur /assets/<NAME>, shot = sublayer. Cases par link : un shader par géo, une anim par rig (anims off par défaut), proxy par groom.
/obj (SOP)Menu Géométrie : proxy ou géo complète.

Autres HDA : FLUX Anim (une ligne par perso, anim de plan ou clip, noise de rotation, bouton « Persos du plan »), FLUX Shot, FLUX Crowd, FLUX Lighting, FLUX Sequence, FLUX Export.

Maya

USD aplati en .usda temporaire (défaut, gère les chemins accentués) ou mayaUsdProxyShape (garde les variantes). Les imports FLUX sont tagués pour le bouton MAJ.

Autres logiciels

Import natif du LAST ou de la vNNN (Read Nuke, ouverture Photoshop, import ZBrush...).

A11. Page USD : components, décors, shots

La page USD ouvre la Bibliothèque : assets (components), décors (assemblies), et l'état des shots.

Component (un asset prêt à charger)

  1. Nouveau component : choisir l'asset et ses départements (une fois chacun).
  2. Le component est fait de blocks (model, look, rig par défaut, noms libres, ajout / retrait).
  3. Dans un block, New link : choisir une task puis un publish (tout format, pas seulement USD) ou un chemin.
  4. Par link : arc Ref / Sublayer / Payload, case Variante + nom, case Proxy, cibles (géos concernées), dépendances.
  5. Ensuite, chaque publish d'un département du component le met à jour (nouvelle version du component).
Une texture seule dans le block look suffit : FLUX écrit un matériau simple (UsdPreviewSurface) et devine la map depuis le nom (BCOL, ROUGH, METAL, NORM, OPACITY, EMISS, DISP, AO, UDIM).

Décor

Un décor (SET) regroupe des instances de components : /<SET>/<CLASS>/<ASSET>_NN, instanciables, avec une variante par instance. Le layout est publié depuis le logiciel.

Shot

Le stage du shot est généré par FLUX depuis Production (casting, plage) et les publishs du shot. Ordre des couches, de la plus forte à la plus faible :

lighting
light rig du shot, publish LIGHT
fx, simulation
caches FX / CFX
crowd
agents FLUX Crowd
animation
anim de chaque perso sur son instance
layout
caméra, placement
casting
les components et décors du plan
sequence
light rig de séquence

Rien n'a changé = pas de nouvelle version. Une version peut être figée.

A12. Production

  • Tableau des assets et des shots, détail par tâche (onglets de tâches ouverts gardés).
  • Synchronisation avec le disque : ce qui est créé dans Production est créé sur le disque et inversement. Elle ne supprime jamais rien toute seule.
  • Créer / renommer une séquence ou un shot : champ numéro (3 chiffres) + champ secondaire (1 chiffre). Vide = dizaine suivante ; 1 → 0010 ; 1 et 5 → 0015. Un renommage déplace aussi les dossiers, refusé si le shot contient déjà des publishs.
  • Casting par séquence et par shot, avec nombre d'instances (boutons − / +).
  • Plage d'images par shot (utilisée par le stage et le rendu).
  • Verrouiller une séquence ou un shot (panneau Edit) : champs grisés, pas de suppression ni de renommage. Déverrouiller demande de taper un mot de confirmation.
  • Archiver / supprimer : un shot, une séquence ou un asset archivé part dans les archives avec ses tokens ; il ne revient pas.
  • Scène de rendu Houdini (sur une séquence) : voir A18.
  • Ouvrir dans le Folder Manager.

A13. Calendrier et Activité

Calendrier

  • Vues mois (défilement continu sur 18 mois) et semaine, filtre par personne, une couleur par personne.
  • Un engagement pour toi est engagé directement ; pour quelqu'un d'autre, c'est une proposition qui le mentionne : il accepte, décale puis accepte, ou refuse.
  • Les publishs du projet apparaissent par jour ; une bande se déplie en heure, personne, fichier.

Activité

Fil de tout ce qui se passe (publishs, créations, archives, messages), mentions non lues, actions directes depuis une ligne (ouvrir, aller au fichier).

A14. Shelf Manager et Template Editor

Shelf Manager

  • Installer / Mettre à jour / Retirer le shelf FLUX de Maya et Houdini, le plugin ZBrush, les bridges des autres logiciels.
  • Houdini : installer copie le shelf et construit les HDA FLUX (même si Houdini est ouvert). Retirer le shelf garde les HDA.
  • Outils cochables un par un. Aperçu du shelf pour Maya, Houdini, ZBrush.
  • Maya : outils CAM (rig caméra) et LIGHT (rig de lumières) de l'équipe.

Template Editor

Presets de scènes et d'arborescences : ce que FLUX crée quand on lance un logiciel « New Scene » sur un asset ou un shot. Preset livré Rendu <SEQ> qui ouvre la scène de rendu de séquence.

A15. Disque : taille et nettoyage

  • Taille des projets et des dossiers.
  • Nettoyage d'un asset ou d'un projet : FLUX compare au rangement actuel, remet les publishs mal rangés à leur place, retire les doublons identiques. Seulement ce qui est sûr ; le reste est signalé. Tout est annulable (journal .flux_cleanup/).
  • Clone propre d'un projet.

A16. Paramètres avancés et Graph YAML

Paramètres avancés

  • Conversion des textures en .tx au publish (activée par défaut, désactivable par poste).
  • Proxy USD au publish (activé par défaut, désactivable par poste).
  • Accès au Graph YAML.

Graph YAML

Affiche chaque action de FLUX (publish, conversion de texture, proxy...) sous forme de nodes : entrées, commandes, sorties. Mode Éditer : palette de nodes (commandes FLUX, nodes de l'équipe dans CONFIG/nodes/, fonctions internes), Tab sous la souris pour chercher un node. Réservé aux TD : une action modifiée change le comportement pour toute l'équipe.

A17. FLUX dans chaque logiciel

Quand tu commences à travailler dans un logiciel avec FLUX : Shelf Manager → choisis le logiciel → Installer (shelf, HDA ou plugin, voir A14), puis relance le logiciel. Une seule fois par poste.

A18. Lighting et rendu

  1. Production → séquence → Scène de rendu Houdini : crée shot/<SEQ>/<SEQ>_render.hip depuis le template de l'équipe. Jamais écrasée si elle existe.
  2. Contenu : FLUX Sequence + COMMON_LIGHTS, puis par shot : FLUX Shot → SHOT_LIGHTS → Karma Cryptomatte → Karma Render Settings (résolution projet, AOV) → OUT + ROP Karma.
  3. Light rig de séquence (plus faible) + light rig de shot (au-dessus). Publish LIGHT → couche lighting du stage.
  4. Rendu Karma (usdrender / husk) en .exr multi-parties avec AOV et cryptomattes.
  5. Farm Tractor du studio : prévu. À la soumission, chaque LAST sera remplacé par sa vNNN (la farm ne lira jamais un LAST).
  6. Environnement du studio : tout ce qui est propre à la farm d'un studio (moteur Tractor, chemins Houdini et denoise des blades, tags de limite, motif des salles) est dans un fichier d'environnement lié depuis CONFIG/studio.json (clé environment, chemin relatif au dossier FLUX ou réseau). Il est vide par défaut. Il se règle dans Rendu > Avancé > Environnement du studio (rôle lead ou supervisor). Priorité : réglage du projet (render.json), puis environnement, puis vide.

A19. Règles de travail

  1. Tout nouveau nom (asset, shot, tâche) se crée dans FLUX, jamais dans l'explorateur Windows.
  2. Ne renomme, ne déplace, n'efface jamais un publish à la main. Une version publiée ne se modifie pas : on republie.
  3. Travaille sur les LAST, fige en vNNN pour le rendu final.
  4. Un publish = un département. La géo dans GEO, les matériaux dans SHADING, le squelette dans RIG.
  5. Écris un commentaire de publish utile : c'est la note que l'équipe lira.
  6. En USD, charge des produits (asset, décor, shot), pas des couches.
  7. Garde FLUX ouvert quand tu publies depuis un logiciel.
  8. Unités : 1 unité = 1 mètre, axe Y en haut (référence Houdini). Mets Maya à l'échelle.
  9. Le chat et les mentions remplacent les messages perdus : mentionne la personne concernée.
  10. Si quelque chose semble faux, ouvre la console (barre de titre) et envoie le log à l'équipe pipe.

B9. Moteur d'actions YAML

Inspiré de Silex. flux_core (aucune dépendance FLUX ni DCC) exécute des actions décrites en YAML ; flux_actions fournit les commandes et la config.

  • Actions livrées : publish, publish_maya, publish_houdini, conform_texture, generate_proxy.
  • Une action = des étapes ; une étape = des commandes ; une commande = une classe Python avec execute qui retourne des clés (sorties).
  • graph.py transforme le YAML en graphe pour l'UI : node Entrées (contexte + paramètres posés par le runner, lus par AST), commandes, sorties, notes = commentaires YAML.
  • Éditeur (ADR 0039 / 0040) : palette = commandes + CONFIG/nodes/*.py + fonctions publiques de features / core / dcc (node call_function), liens de port à port.
Piège : un nouveau YAML dans flux_actions/config/ doit être tracké (exception !backend/flux_actions/config/*.yml du .gitignore, vérifier avec git check-ignore).

B13. Textures (.tx) et proxies

Conversion .tx (texture_conform.py)

OpenImageIO make_texture : mip-maps, tuiles, colorspace selon le rôle de la map et le conteneur, hash de la source dans ImageDescription (pas de reconversion inutile), UDIM, parallèle. Karma lit le .tx. Pas d'imaketx (licence Houdini), pas de .rat.

Conversion par map (dcc/texture_convert.py)

FORMAT_DEPTHS : profondeurs possibles par format ; needs_convert : si le logiciel a déjà écrit le bon format, le fichier est gardé tel quel.

Proxy USD (usd_proxy.py)

pxr + fast-simplification (MIT) + numpy : décimation (20 000 → ~2 000 triangles), purpose=proxy. Groom (ADR 0026) : BasisCurves réduites (1 courbe sur 10), largeurs et skin gardés. Un link Proxy manuel gagne.
